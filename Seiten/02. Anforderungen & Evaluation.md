## Anforderungen
### Funktionale Anforderungen
Die Monitoring-Plattform muss folgende Funktionen bereitstellen:

- Infrastrukturmetriken zentral mit Prometheus erfassen.
- Monitoring-Daten in Grafana visualisieren.
- Eine FortiGate Firewall, eine Azure Windows Server VM und eine On-Premises Windows Server VM als vorgesehene Zielsysteme unterstützen.
- Mindestens zwei der drei Zielsysteme im MVP erfolgreich integrieren.
- Für erfolgreich integrierte Systeme relevante Metriken in Prometheus erfassen und in Grafana darstellen.
- Über Alertmanager definierte Zustände überwachen und mindestens einen Testalarm per E-Mail zustellen.
- Mindestens zwei Mandanten beziehungsweise Organisationen logisch voneinander trennen.
- Monitoring-Konfigurationen soweit sinnvoll versioniert als Code verwalten.
- Die Bereitstellung der Monitoring-Konfiguration über eine Azure-DevOps-Pipeline ermöglichen.
  
---

### Nichtfunktionale Anforderungen
Die Monitoring-Plattform soll folgende nichtfunktionale Anforderungen erfüllen:

- **Nachvollziehbarkeit:** Architektur, Konfigurationen, Entscheide und Testergebnisse werden nachvollziehbar dokumentiert.
- **Reproduzierbarkeit:** Monitoring-Konfigurationen werden soweit sinnvoll versioniert und über Git sowie Azure DevOps bereitstellbar gehalten.
- **Wartbarkeit:** Die Lösung soll modular aufgebaut sein und Änderungen an Dashboards, Alert-Regeln und Monitoring-Konfigurationen ohne unnötige Abhängigkeiten ermöglichen.
- **Erweiterbarkeit:** Weitere Zielsysteme, Metriken und Monitoring-Komponenten sollen später ergänzt werden können, ohne die grundlegende Plattformarchitektur neu aufzubauen.
- **Sicherheit:** Berechtigungen und Zugriffe folgen dem Least-Privilege-Prinzip. Zugangsdaten und Secrets dürfen nicht ungeschützt in Repositorys abgelegt werden.
- **Mandantenfähigkeit:** Im MVP muss eine logische Trennung von mindestens zwei Mandanten beziehungsweise Organisationen nachgewiesen werden. Eine produktionsreife Mandantentrennung ist nicht Bestandteil des MVP.
- **Betriebsaufwand:** Die Lösung soll mit möglichst geringem Konfigurations- und Administrationsaufwand betrieben werden können.
- **Wirtschaftlichkeit:** Zusätzliche Lizenz- und Cloudkosten sollen möglichst vermieden beziehungsweise bei der Bewertung transparent berücksichtigt werden.

---

### Technische Rahmenbedingungen
Für die Umsetzung des Monitoring-MVP gelten folgende technische Rahmenbedingungen:

- Die Monitoring-Plattform wird auf einer **Kubernetes-Testumgebung** betrieben.
- **Prometheus, Grafana und Alertmanager** bilden die zentralen Monitoring-Komponenten.
- Die Bereitstellung erfolgt über geeignete **Helm Charts oder Kubernetes-Manifeste**.
- Als primäre Zielsysteme dienen eine **FortiGate Firewall**, eine **Azure Windows Server VM** und eine **On-Premises Windows Server VM**.
- Für die Systemanbindung werden die evaluierten Exporter und Schnittstellen eingesetzt, insbesondere **Windows Exporter** und **Blackbox Exporter**.
- Quellcode, Infrastrukturdefinitionen und Monitoring-Konfigurationen werden in **Git** versioniert.
- **Azure DevOps** wird für das technische Repository sowie mindestens eine CI/CD-Pipeline verwendet.
- Die CI/CD-Pipeline soll die versionierte Monitoring-Konfiguration automatisiert in die Testumgebung bereitstellen.
- Dashboards, Alert-Regeln und weitere Monitoring-Konfigurationen werden soweit sinnvoll nach dem Prinzip **Monitoring-as-Code** verwaltet.
- Für Administration und Umsetzung stehen Werkzeuge wie **Git, kubectl, Helm, Azure CLI und Visual Studio Code** zur Verfügung.
- Die Netzwerkerreichbarkeit und notwendige Firewallfreigaben zu den jeweiligen Monitoring-Zielsystemen müssen für die technische Umsetzung gegeben sein.

---

### Sicherheitsanforderungen
Für den Monitoring-MVP gelten folgende Sicherheitsanforderungen:

- **Least Privilege:** Benutzer, Service Accounts und technische Zugriffe erhalten nur die für ihre Aufgabe erforderlichen Berechtigungen.
- **Secrets:** Passwörter, API-Tokens und andere Zugangsdaten dürfen nicht im Klartext in Git-Repositories oder der Projektdokumentation gespeichert werden.
- **Netzwerkzugriff:** Monitoring-Endpunkte und Exporter dürfen nur über die erforderlichen Netzwerkpfade und Firewallfreigaben erreichbar sein.
- **Keine unnötige Exponierung:** Überwachte Systeme und Exporter sollen für das Monitoring nicht direkt gegenüber dem Internet exponiert werden.
- **Mandantentrennung:** Für mindestens zwei Mandanten beziehungsweise Organisationen wird eine logische Zugriffstrennung umgesetzt. Eine vollständig produktionsreife Mandantentrennung ist nicht Bestandteil des MVP.
- **Testdaten:** Für die Semesterarbeit werden keine produktiven Kundendaten verwendet. Tests erfolgen mit geeigneten internen oder dafür vorgesehenen Testsystemen.
- **Nachvollziehbarkeit:** Sicherheitsrelevante Konfigurationen und bekannte Einschränkungen werden dokumentiert und soweit sinnvoll versioniert.

## Evaluation der Systemanbindung

### FortiGate
Für die FortiGate soll eine Monitoring-Anbindung evaluiert werden, welche sich in die zentrale Prometheus- und Grafana-Plattform integrieren lässt. Im bestehenden Monitoring der Intecso AG wird primär die Erreichbarkeit der Firewalls überwacht.

Für den MVP wird deshalb die **Erreichbarkeit der FortiGate** als grundlegende Monitoring-Anforderung definiert. Eine detaillierte Erfassung interner Systemmetriken ist nicht zwingend erforderlich.

#### Mögliche Anbindungsvarianten [FortiGate]
1. **Prometheus SNMP Exporter**  
   Die FortiGate stellt System- und Netzwerkmetriken über SNMP bereit. Der SNMP Exporter fragt diese ab und stellt sie Prometheus zur Verfügung. Dadurch ist ein deutlich detaillierteres Monitoring als eine reine Verfügbarkeitsprüfung möglich.

2. **FortiOS REST API / FortiGate Exporter**  
   Über die FortiOS REST API können Systeminformationen und Statistiken abgefragt werden. Für die Integration mit Prometheus kann ein entsprechender Exporter eingesetzt werden. Dafür werden ein API-Administrator und ein API-Token benötigt.

3. **Prometheus Blackbox Exporter**  
   Der Blackbox Exporter überprüft die FortiGate mittels ICMP auf Erreichbarkeit. Dies entspricht weitgehend dem heutigen Monitoring und benötigt keine zusätzlichen Zugangsdaten auf der Firewall.

Eine Einschränkung besteht darin, dass nicht alle betreuten FortiGate Firewalls von der Monitoring-Plattform direkt erreichbar sind. Die Geräte sind jedoch in FortiGate Cloud registriert. FortiGate Cloud bietet Remote-Management und eine Cloud REST API und wird deshalb als mögliche spätere Erweiterung berücksichtigt.

>- [Fortinet – FortiOS API](https://docs.fortinet.com/document/fortigate/6.4.9/administration-guide/940602/using-apis)
>- [Prometheus – SNMP Exporter](https://github.com/prometheus/snmp_exporter/tree/main/generator)
>- [Prometheus – Blackbox Exporter](https://github.com/prometheus/blackbox_exporter)
>- [Fortinet – FortiGate Management über FortiCloud](https://docs.fortinet.com/document/forticloud/26.3.0/forticloud-concept-guide/866368/fortigate-management)
>- [Prometheus Community – FortiGate Exporter](https://github.com/prometheus-community/fortigate_exporter)

#### Bewertung der Anbindungsvarianten [FortiGate]
Die Varianten werden auf einer Skala von **1 bis 5** bewertet. Eine hohe Punktzahl bedeutet eine gute Erfüllung des jeweiligen Kriteriums.

| Kriterium | Gewichtung | SNMP Exporter | REST API / FortiGate Exporter | Blackbox Exporter |
|---|---:|---:|---:|---:|
| Abdeckung der MVP-Anforderungen | 25 % | 5 | 5 | 5 |
| Direkte Prometheus-Integration | 20 % | 4 | 4 | 5 |
| Implementierungsaufwand | 20 % | 3 | 2 | 5 |
| Netzwerk und Sicherheit | 15 % | 3 | 3 | 4 |
| Berechtigungen und Abhängigkeiten | 10 % | 3 | 2 | 5 |
| Laufende Kosten | 10 % | 5 | 5 | 5 |
| **Gewichtetes Ergebnis** | **100 %** | **3,85** | **3,55** | **4,80** |

##### SNMP Exporter

**Vorteile:**
- Detaillierte System- und Netzwerkmetriken
- Read-only-Zugriff auf die FortiGate
- Direkte Integration in Prometheus

**Nachteile:**
- Zusätzliche SNMP-Konfiguration notwendig
- Höherer Aufwand als für eine reine Erreichbarkeitsprüfung
- Direkte Netzwerkerreichbarkeit zur FortiGate erforderlich

**Kosten:**  
Keine zusätzlichen Lizenzkosten. Es entsteht Betriebs- und Konfigurationsaufwand.

##### FortiOS REST API / FortiGate Exporter

**Vorteile:**
- Abfrage detaillierter FortiGate-Informationen
- Prometheus-Integration über einen Exporter
- Kommunikation über HTTPS

**Nachteile:**
- API-Administrator und Token notwendig
- Zusätzliche Secrets müssen verwaltet werden
- Community-basierter Exporter als zusätzliche Abhängigkeit
- Höherer Aufwand als für den benötigten MVP-Umfang

**Kosten:**  
Für den Exporter fallen keine Lizenzkosten an. Zusätzlicher Aufwand entsteht für Konfiguration, Token-Verwaltung und Betrieb.

##### Blackbox Exporter

**Vorteile:**
- Sehr geringer Implementierungsaufwand
- Direkte Integration in Prometheus
- Keine Zugangsdaten auf der FortiGate notwendig
- Entspricht dem heutigen Verfügbarkeitsmonitoring

**Nachteile:**
- Keine internen Systemmetriken
- Direkte ICMP-Erreichbarkeit notwendig
- Nicht für alle betreuten FortiGate Firewalls einsetzbar

**Kosten:**  
Keine zusätzlichen Lizenzkosten. Es entsteht lediglich Betriebs- und Konfigurationsaufwand innerhalb der eigenen Monitoring-Plattform.

#### Empfehlung für den MVP [FortiGate]

Für den MVP wird die **Erreichbarkeitsüberwachung über den Prometheus Blackbox Exporter mittels ICMP** gewählt. Sie erfüllt die definierten Anforderungen mit dem geringsten Implementierungs- und Betriebsaufwand.

Für nicht direkt erreichbare Firewalls wird **FortiGate Cloud** als mögliche spätere Erweiterung dokumentiert. Eine Integration der Cloud REST API ist nicht Bestandteil des MVP.

##### Einschränkungen und offene Punkte [FortiGate]
- ICMP-Monitoring setzt voraus, dass die FortiGate von der Monitoring-Plattform aus direkt erreichbar ist.
- Nicht alle betreuten FortiGate Firewalls verfügen über eine entsprechend erreichbare IP-Adresse.
- Für diese Geräte ist die Überwachung über FortiGate Cloud eine mögliche spätere Erweiterung, wird im MVP jedoch nicht umgesetzt.
- Detaillierte Firewall-Metriken über SNMP oder REST API sind nicht Bestandteil des MVP.

### Azure Windows Server
Für die Azure Windows Server VM soll eine Monitoring-Anbindung evaluiert werden, welche sich in die zentrale Prometheus- und Grafana-Plattform integrieren lässt. Die Anforderungen orientieren sich an den heute überwachten Azure Windows Server VMs der Intecso AG und deren Kundschaft.

Im bestehenden Monitoring werden abhängig vom Server unter anderem folgende Werte überwacht:

- Erreichbarkeit mittels Ping
- CPU-Auslastung
- Arbeitsspeicherauslastung
- freier Speicherplatz einzelner Laufwerke
- System-Uptime
- Pagefile-Auslastung
- Erreichbarkeit von RDP
- Status betriebsrelevanter Dienste und Applikationskomponenten
- DNS-Funktion beziehungsweise DNS-Dienste

Bei den Diensten kann es sich sowohl um Windows-Systemdienste als auch um Komponenten von Drittanbieter-Applikationen, Datenbanken oder kundenspezifischen Fachanwendungen handeln.

Für den MVP werden **Ping, CPU-Auslastung, Arbeitsspeicher, freier Speicherplatz und System-Uptime** als grundlegende Monitoring-Anforderungen definiert. RDP, Pagefile, DNS und applikationsspezifische Dienste gelten als optionale Erweiterungen.

#### Mögliche Anbindungsvarianten [Azure Windows VM]
1. **Prometheus Windows Exporter**  
   Der windows_exporter wird auf der Windows Server VM installiert und stellt System- und Applikationsmetriken direkt im Prometheus-Format bereit. Über verschiedene Collector können unter anderem CPU, Arbeitsspeicher, Laufwerke, Netzwerk, Pagefile und Dienste überwacht werden.

2. **Azure Monitor mit Azure Monitor Agent**  
   Azure Monitor stellt eine native Azure-Lösung zur VM-Überwachung bereit. Hostmetriken werden teilweise automatisch erfasst. Für Gastmetriken und Protokolle können der Azure Monitor Agent und Data Collection Rules eingesetzt werden.

3. **Windows Exporter mit Blackbox Exporter**  
   Der windows_exporter erfasst interne Systemmetriken. Der Blackbox Exporter ergänzt externe Verfügbarkeitsprüfungen über beispielsweise ICMP, TCP oder HTTP/HTTPS.

>**Quellen:**
>- [Prometheus Community – windows_exporter](https://github.com/prometheus-community/windows_exporter)
>- [Microsoft Learn – Überwachen virtueller Computer in Azure](https://learn.microsoft.com/de-de/azure/azure-monitor/vm/monitor-vm)
>- [Microsoft Learn – Gastprotokolle und Metriken einer Azure VM sammeln](https://learn.microsoft.com/de-de/azure/azure-monitor/vm/tutorial-monitor-vm-guest)
>- [Prometheus – Blackbox Exporter](https://github.com/prometheus/blackbox_exporter)

#### Bewertung der Anbindungsvarianten [Azure Windows VM]
Die Varianten werden auf einer Skala von **1 bis 5** bewertet. Eine hohe Punktzahl bedeutet eine gute Erfüllung des jeweiligen Kriteriums.

| Kriterium | Gewichtung | Windows Exporter | Azure Monitor | Windows + Blackbox Exporter |
|---|---:|---:|---:|---:|
| Abdeckung der MVP-Metriken | 25 % | 5 | 4 | 5 |
| Direkte Prometheus-Integration | 20 % | 5 | 2 | 5 |
| Implementierungsaufwand | 15 % | 4 | 3 | 3 |
| Netzwerk und Sicherheit | 15 % | 3 | 5 | 3 |
| Berechtigungen und Abhängigkeiten | 10 % | 4 | 3 | 4 |
| Laufende Kosten | 15 % | 5 | 2 | 5 |
| **Gewichtetes Ergebnis** | **100 %** | **4,45** | **3,20** | **4,30** |

##### Windows Exporter

**Vorteile:**
- Direkte Prometheus-Integration
- Deckt die benötigten MVP-Systemmetriken ab
- Zusätzliche Collector für Pagefile, Dienste, DNS und weitere Komponenten
- Keine zusätzlichen Lizenzkosten
- Konfiguration versionierbar

**Nachteile:**
- Zusätzlicher Dienst auf der VM
- Prometheus benötigt Netzwerkzugriff auf den Exporter
- Endpunkt und Firewall-Regel müssen abgesichert werden

**Kosten:**  
Keine Lizenzkosten. Aufwand entsteht für Installation, Konfiguration und Betrieb.

##### Azure Monitor mit Azure Monitor Agent

**Vorteile:**
- Native Azure-Integration
- Zentrale Konfiguration über Data Collection Rules
- Host-, Gast- und Logdaten können erfasst werden
- Keine direkte Prometheus-Verbindung zur VM erforderlich

**Nachteile:**
- Keine direkte Integration der Gastmetriken in die eigene Prometheus-Instanz
- Zusätzliche Azure-Abhängigkeit
- Höherer Integrationsaufwand für die geplante Plattform
- Kosten abhängig von der verwendeten Datensammlung

**Kosten:**  
Azure-Hostmetriken werden teilweise kostenlos bereitgestellt. Für Gastprotokolle fallen jedoch Aufnahme- und Speichergebühren an. Je nach Konfiguration können weitere Azure-Monitor-Kosten entstehen.

##### Windows Exporter mit Blackbox Exporter

**Vorteile:**
- Interne Systemmetriken und externe Verfügbarkeitsprüfungen kombinierbar
- ICMP-, TCP-, HTTP- und HTTPS-Prüfungen möglich
- Direkte Integration in Prometheus
- Keine zusätzlichen Lizenzkosten

**Nachteile:**
- Zwei Exporter müssen betrieben werden
- Zusätzliche Netzwerk- und Firewall-Konfiguration
- Höherer Implementierungsaufwand

**Kosten:**  
Keine Lizenzkosten. Gegenüber dem alleinigen Windows Exporter entsteht zusätzlicher Betriebs- und Konfigurationsaufwand.

#### Empfehlung für den MVP [Azure Windows VM]
Für den MVP wird der **Prometheus Windows Exporter** bevorzugt. Er deckt die definierten Systemmetriken direkt ab, lässt sich ohne zusätzliche Azure-Monitor-Abhängigkeit in Prometheus integrieren und verursacht keine zusätzlichen Lizenzkosten.

Der **Blackbox Exporter** kann später ergänzend eingesetzt werden, wenn externe Verfügbarkeits- oder Dienstprüfungen benötigt werden.

##### Einschränkungen und offene Punkte[Azure Windows VM]
- Prometheus benötigt Netzwerkzugriff auf den Windows Exporter der Azure VM.
- Der Exporter-Endpunkt und die erforderliche Firewallfreigabe müssen auf die Monitoring-Plattform beschränkt und abgesichert werden.
- Die konkrete Netzwerkerreichbarkeit zwischen der Monitoring-Plattform und der vorgesehenen Azure Test-VM muss bei der Umsetzung validiert werden.
- Erweiterte Prüfungen wie RDP, Pagefile, DNS oder applikationsspezifische Dienste sind nicht Bestandteil des MVP.

### On-Premises Windows Server
Für die On-Premises Windows Server VM soll eine Monitoring-Anbindung evaluiert werden, welche sich in die zentrale Prometheus- und Grafana-Plattform integrieren lässt. Die Anforderungen orientieren sich an den heute überwachten Windows Servern der Intecso AG und deren Kundschaft.

Im bestehenden Monitoring werden abhängig vom Server unter anderem folgende Werte überwacht:

- Erreichbarkeit mittels Ping
- CPU-Auslastung
- Arbeitsspeicherauslastung
- freier Speicherplatz einzelner Laufwerke
- System-Uptime
- Pagefile-Auslastung
- Erreichbarkeit von RDP
- Status betriebsrelevanter Dienste und Applikationskomponenten
- DNS-Funktion beziehungsweise DNS-Dienste

Bei den Diensten kann es sich sowohl um Windows-Systemdienste als auch um Komponenten von Drittanbieter-Applikationen, Datenbanken oder kundenspezifischen Fachanwendungen handeln.

Für den MVP werden **Ping, CPU-Auslastung, Arbeitsspeicher, freier Speicherplatz und System-Uptime** als grundlegende Monitoring-Anforderungen definiert. RDP, Pagefile, DNS und applikationsspezifische Dienste gelten als optionale Erweiterungen.

Im Unterschied zur Azure Windows Server VM muss bei der On-Premises-Anbindung insbesondere die Netzwerkverbindung zwischen der zentralen Monitoring-Plattform und dem Kundennetz berücksichtigt werden. Die gewählte Lösung soll möglichst wenige Firewallfreigaben benötigen und darf keine unnötige direkte Exponierung des Windows Servers gegenüber dem Internet voraussetzen.

#### Mögliche Anbindungsvarianten [On-Premises Windows VM]
Für die Überwachung der On-Premises Windows Server VM werden folgende Varianten betrachtet:

1. **Prometheus Windows Exporter**  
   Der windows_exporter wird direkt auf dem Windows Server installiert und stellt System- und Applikationsmetriken im Prometheus-Format bereit. Damit können unter anderem CPU, Arbeitsspeicher, Laufwerke, Uptime, Pagefile und Dienste überwacht werden.

   Voraussetzung ist, dass die zentrale Monitoring-Plattform den Exporter im Kundennetz erreichen kann. Dazu ist eine geeignete Netzwerkverbindung, beispielsweise über eine bestehende Site-to-Site-VPN-Verbindung, sowie eine gezielte Firewallfreigabe notwendig.

2. **Windows Exporter mit Blackbox Exporter**  
   Der windows_exporter erfasst die internen Systemmetriken. Ergänzend übernimmt der Blackbox Exporter externe Verfügbarkeitsprüfungen, beispielsweise mittels ICMP oder TCP.

   Auch diese Variante setzt eine Netzwerkerreichbarkeit zwischen Monitoring-Plattform und Kundennetz voraus. Sie bietet gegenüber dem alleinigen Windows Exporter zusätzliche Möglichkeiten für die Prüfung der Erreichbarkeit von Servern und Diensten.

3. **Azure Arc mit Azure Monitor Agent**  
   Der On-Premises Windows Server kann über Azure Arc an Azure angebunden und anschliessend mit dem Azure Monitor Agent überwacht werden. Über Data Collection Rules lassen sich Metriken und Protokolle erfassen.

   Diese Variante benötigt keine direkte Prometheus-Verbindung zum On-Premises-Server, führt jedoch zusätzliche Abhängigkeiten von Azure Arc und Azure Monitor ein. Die gesammelten Daten stehen zudem nicht direkt im vorgesehenen Prometheus-Format zur Verfügung.

Für die weitere Evaluation werden insbesondere Monitoring-Umfang, Netzwerkzugriff, notwendige Firewallfreigaben, Sicherheit, Implementierungsaufwand, Berechtigungen, Kosten und die Integration in die eigene Prometheus- und Grafana-Plattform berücksichtigt.

>- [Prometheus – Blackbox Exporter](https://github.com/prometheus/blackbox_exporter)
>- [Microsoft Learn – Überwachung mit Azure Arc-fähigen Servern](https://learn.microsoft.com/de-de/azure/azure-arc/servers/cloud-native/monitor-alerts)

#### Bewertung der Anbindungsvarianten [On-Premises Windows VM]

Die Varianten werden auf einer Skala von **1 bis 5** bewertet. Eine hohe Punktzahl bedeutet eine gute Erfüllung des jeweiligen Kriteriums.

| Kriterium | Gewichtung | Windows Exporter | Windows + Blackbox Exporter | Azure Arc + Azure Monitor |
|---|---:|---:|---:|---:|
| Abdeckung der MVP-Metriken | 20 % | 5 | 5 | 4 |
| Direkte Prometheus-Integration | 20 % | 5 | 5 | 2 |
| Implementierungsaufwand | 15 % | 4 | 3 | 2 |
| Netzwerk und Sicherheit | 20 % | 3 | 3 | 5 |
| Berechtigungen und Abhängigkeiten | 10 % | 4 | 4 | 2 |
| Laufende Kosten | 15 % | 5 | 5 | 2 |
| **Gewichtetes Ergebnis** | **100 %** | **4,30** | **4,15** | **3,05** |

##### Windows Exporter

**Vorteile:**

- Direkte Bereitstellung der Metriken im Prometheus-Format
- Deckt die benötigten MVP-Systemmetriken ab
- Erweiterbar um Dienste und weitere Windows-Metriken
- Keine zusätzlichen Lizenzkosten
- Geringe zusätzliche Abhängigkeiten

**Nachteile:**

- Prometheus benötigt Netzwerkzugriff auf den On-Premises-Server
- Firewallfreigabe für den Exporter notwendig
- Sichere Verbindung zwischen Monitoring-Plattform und Kundennetz erforderlich
- Exporter-Endpunkt muss abgesichert werden

**Kosten:**  
Keine Lizenzkosten. Aufwand entsteht für Installation, Netzwerkfreigabe, Konfiguration und Betrieb.

##### Windows Exporter mit Blackbox Exporter

**Vorteile:**

- Interne Systemmetriken über den Windows Exporter
- Zusätzliche ICMP-, TCP-, HTTP- oder HTTPS-Prüfungen möglich
- Direkte Integration in Prometheus
- Keine zusätzlichen Lizenzkosten

**Nachteile:**

- Zwei Exporter müssen konfiguriert und betrieben werden
- Zusätzlicher Konfigurationsaufwand
- Netzwerkerreichbarkeit zum Kundennetz weiterhin notwendig
- Je nach Prüfungen zusätzliche Firewallfreigaben erforderlich

**Kosten:**  
Keine Lizenzkosten. Gegenüber dem alleinigen Windows Exporter entsteht zusätzlicher Betriebs- und Konfigurationsaufwand.

##### Azure Arc mit Azure Monitor

**Vorteile:**

- Geeignet für die zentrale Verwaltung von On-Premises-Servern
- Keine direkte eingehende Prometheus-Verbindung zum Server erforderlich
- Integration in Azure Monitor und Data Collection Rules
- Gute Eignung für hybride IT-Umgebungen

**Nachteile:**

- Keine direkte Bereitstellung der Metriken für die eigene Prometheus-Instanz
- Zusätzliche Abhängigkeit von Azure Arc und Azure Monitor
- Höherer Implementierungs- und Integrationsaufwand für den MVP
- Azure-Berechtigungen und zusätzliche Cloud-Konfiguration erforderlich

**Kosten:**  
Grundlegende Azure-Arc-Verwaltungsfunktionen sind kostenlos. Bei Verwendung zusätzlicher Azure-Dienste wie Azure Monitor können jedoch nutzungsabhängige Kosten, beispielsweise für Datenerfassung und Aufbewahrung, entstehen.

#### Empfehlung für den MVP [On-Premises Windows VM]
Für den MVP wird der **Prometheus Windows Exporter** bevorzugt. Er deckt die benötigten Systemmetriken direkt ab, stellt diese nativ für Prometheus bereit und verursacht keine zusätzlichen Lizenzkosten. windows_exporter unterstützt unter anderem CPU-, Arbeitsspeicher-, Laufwerks-, System- und Dienstmetriken.

Voraussetzung ist eine **gesicherte Netzwerkverbindung zwischen der Monitoring-Plattform und dem Kundennetz** sowie eine gezielte Firewallfreigabe für den Exporter. Der Windows Server soll dabei nicht direkt über das Internet exponiert werden.

Der **Blackbox Exporter** kann später für zusätzliche Verfügbarkeits- und Dienstprüfungen ergänzt werden. **Azure Arc mit Azure Monitor** wird für den MVP nicht gewählt, da dadurch zusätzliche Azure-Abhängigkeiten entstehen und die Metriken nicht direkt in die vorgesehene Prometheus-Integration fliessen. Azure Arc hätte hinsichtlich der Netzwerkanbindung allerdings den Vorteil, dass der Connected Machine Agent grundsätzlich ausgehend über HTTPS/TCP 443 kommuniziert. Netzwerkanforderungen an verbundene Maschinenagenten.

##### Einschränkungen und offene Punkte [On-Premises Windows VM]
- Die Umsetzung setzt eine gesicherte Netzwerkverbindung zwischen der Monitoring-Plattform und dem On-Premises-Netz voraus.
- Der Zugriff auf den Windows Exporter muss durch gezielte Firewallfreigaben auf die Monitoring-Plattform beschränkt werden.
- Die konkrete Netzwerkanbindung und Erreichbarkeit der vorgesehenen Test-VM muss bei der technischen Umsetzung validiert werden.
- Erweiterte Prüfungen über den Blackbox Exporter sowie applikationsspezifische Dienste sind nicht Bestandteil des MVP und können später ergänzt werden.

### Abnahmekriterien

#### Monitoring

Das Monitoring gilt im Rahmen des MVP als erfolgreich abgenommen, wenn folgende Kriterien erfüllt sind:

- Mindestens **zwei der drei evaluierten Zielsysteme** (FortiGate, Azure Windows Server VM, On-Premises Windows Server VM) sind erfolgreich an die Monitoring-Plattform angebunden.
- Für jedes erfolgreich angebundene Zielsystem liefert Prometheus verwertbare Metriken und der jeweilige Target-Status ist erfolgreich.
- Die erfassten Metriken werden in Grafana nachvollziehbar visualisiert.
- Für eine angebundene Windows Server VM werden mindestens **CPU-Auslastung, Arbeitsspeicher, freier Speicherplatz und System-Uptime** erfasst.
- Für eine mittels Blackbox Exporter angebundene FortiGate wird mindestens die **Erreichbarkeit mittels ICMP** erfasst.
- Ein Ausfall beziehungsweise eine fehlgeschlagene Metrikerfassung eines angebundenen Zielsystems ist in Prometheus nachvollziehbar erkennbar.
- Die verwendete Anbindungsvariante entspricht der dokumentierten Evaluation oder eine Abweichung wird begründet dokumentiert.

**Abnahmenachweis:**  
Prometheus-Target-Status, beispielhafte Prometheus-Metriken und zugehörige Grafana-Visualisierungen werden während der technischen Abnahme dokumentiert.
